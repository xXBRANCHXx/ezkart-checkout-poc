# Seller onboarding — implementation and remaining verification

The owner approved a minimum seller age of **18** on 28 September 2026. This is Ezkart's owner policy, not a claim about a statutory PSE age threshold. The declared date of birth is validated as a real calendar date and against the current Indonesian (WIB/UTC+7) date; a 29 February birthday reaches the next age on 1 March in a non-leap year. A declaration never establishes verified identity or age.

The merchant's **Seller onboarding** workspace reuses current-owner Wallet verification and verified Supabase email, the existing bank catalog and shipping/map editor. It saves legal name, date of birth, phone, immutable bank versions, and explicit confirmation of the current pickup and return address/pin revision. Pickup and return may share an address. Saved bank numbers are masked on reads and never stored in browser storage. Sensitive content uses the Wallet proof expiry lock. Profile/bank saves retry a lost response once using the exact same intent and key; reload reads the server's current version before any subsequent write. Revision conflicts require a refresh.

Migration `0071_seller_onboarding.sql` adds declarations, immutable bank versions, an 18+ policy, and readiness gates. It intentionally does **not** backfill existing merchants as complete. The signed internal onboarding API is reached through the existing CSRF/account/store/fresh-proof PHP Wallet proxy. Ordinary merchant bearer tokens, extra caller identity fields and `verified` flags cannot create verification evidence.

New production-environment checkout orders, SNAP payment binding, seller-wallet enrollment/provider binding, withdrawal reservations and payment grants recheck readiness in the database transaction. An unverified merchant may explore the dashboard and save declarations but cannot start those money actions. The Wallet UI directs a ready seller to its existing exactly-one Sub-Account enrollment flow. Existing uncertain wallet registrations keep their original request and provider binding; no replacement or blind register retry is introduced. Existing payment receipts, withdrawal lookup, cancellation where still allowed, and already-started payment recovery remain available when onboarding later becomes incomplete.

New merchant withdrawal requests provide a saved bank revision, not an arbitrary destination. The server freezes the corresponding exact account, including leading zeros. Changing the bank does not redirect historical requests; it prevents a new payment dispatch for an older bank version. An existing dispatch retains its original immutable bank, confirmation, receipt and reconciliation path. DOKU bank inquiry remains a separate beneficiary check and does not establish identity/age verification.

Identity evidence is bound to an immutable `identity_revision` containing owner, legal name and declared DOB. Phone, bank, shipping and pin-confirmation changes retain that revision. Legal name, DOB or owner changes create a new identity revision and invalidate the prior proof. Identity status is independent of overall readiness, so an already-verified person with an unconfirmed address sees only the missing address requirement.

## Deliberately unfinished integration

`seller_authenticated_identity` is an **empty trusted view**, so production readiness remains closed. The owner has not selected an operational verification method. A later reviewed implementation must provide authenticated evidence from either an approved identity service or authorized staff reviewing actual evidence, with seller, owner, identity revision, verified age, review/provider reference, policy version and expiry. Its currently named `profile_revision` column means `identity_revision`; `provider_reference` may identify an authenticated internal review. It must handle evidence intake/privacy/retention, access control, audited decisions, correction/revocation and expiry. A self-reported birthday, model opinion, seller checkbox, DOKU registration or bank inquiry cannot fill this source. No raw ID numbers or photos are collected by this slice.

Company-seller identity and bank-beneficiary matching policy is also not supplied; this change does not invent one. DOKU account registration/confirmation, treasury funding, actual provider acceptance and the main-site release hold retain their existing gates. No real ID, bank/provider request, wallet registration, migration deployment or live money action was performed for these checks.
